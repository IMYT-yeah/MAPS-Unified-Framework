四、环境再现流程（三件套，与 09-09 蓝图逐条对齐）

  1. git 全局面具（lake 内部所有 fetch 走镜像）： git config --global url."https://ghfast.top/https://github.com/".insteadOf "https://github.com/" git config --global core.longpaths true # Windows 长路径（mathlib 深层目录）
  2. cache 服务器（已迁移）：https://cache.mathlib.org/mathlib4（旧 olean-cache.lean-lang.org = NXDOMAIN）； 下载路径内容寻址 /f/{hash}.ltar，落地 ~/.cache/mathlib/。
  3. post_update 钩子：根工程 update 后自动 lake exe cache get；⚠️ 必须在根工程跑（子目录跑会触发嵌套克隆）。

实测耗时：cache get 单线程 23:44:13 → 04:42:08 = 4h58m（下载 451MB ＋ 解压 8892 个 .ltar）。 lake build 首次 04:42:19 → 04:56:55（14.6 min，其中 StormPoC 自身 674 s）；后续增量重编 100–124 s。

五、过程记录：两处踩坑（可复用）

  1. ⚠️ 不要在 lake 正在解压时用别的进程读同一批 .ltar。 本轮为统计「每包目标库名」用 16 线程并发读了 8892 个 .ltar 的头部 ⟹ cache get 立刻开始报 C:\…\62b897688f2651ba.ltar: 拒绝访问。（os error 5）， 最终 exit=1、6694 decompression(s) failed。Windows 句柄共享冲突所致。 ✅ 幸而产物仍达到全量（olean 8905）⟹ 未影响 build。下次要统计就等解压结束再扫。
  2. ⭐ leantar 自带并行解压接口，本轮白等了 5 小时： leantar -x -j - --jobs <N> # '-j -' 表示 stdin 读 JSON # JSON: { file: "x.ltar", base?: "<解包根>", hash?: "..." } --jobs N 默认就是 num CPUs，而 lake exe cache get 走的是单线程路径。 ⟹ 下次换机重来：先 cache get（下载），再用 leantar --jobs N 自己并行解压，可省约 4 小时。 （本轮实测单线程解压速率 ≈ 0.5 个文件/秒；而目标盘裸写小文件可达 617 个/秒 ⟹ 瓶颈在 leantar 的每文件开销，不在磁盘。）
